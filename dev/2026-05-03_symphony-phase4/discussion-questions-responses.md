## Sample Selection (SS1)

### Q1 — Cluster-selection rule

**Decision:** Hybrid. For low samples, prioritize richest tension (clearest DA/Pragmatist disagreement). For med/high samples, prioritize densest persona convergence + densest unique insights jointly.

**Why:** Maximizes prompt-failure detection across all three Phase 4 prompts. Each prompt is most likely to fail at a different signal: low-effort fails when tension gets smoothed; med/high full-synthesis fails on aggregation pressure (convergence) and on dropping unique single-persona insights.

**Action for SS1 task file:** No change — already pinned to hybrid in the task prompt. Confirms default.

### Q2 — Cluster-shape diversity within (topic, med) and (topic, high)

**Decision:** **Hard constraint.** The two `med` (and two `high`) clusters per topic MUST differ in cluster-shape (e.g., one strategy-heavy + one tactical, or one human-centered + one structural).

**Why:** Soft preference risks SS1 picking the two highest-signal clusters at the same shape and missing within-shape variance. Hard constraint guarantees RG1's within-effort comparison (med-A vs. med-B; high-A vs. high-B) tests prompt-stability across genuinely different cluster types — which is the within-effort signal RG1 needs.

**Tradeoff accepted:** SS1 may reach for the second-best high-signal cluster within a (topic, effort) cell when the top two cluster candidates share a shape. Acceptable cost for the cleaner within-effort regression signal.

**Action for SS1 task file:**
- Change "soft preference" wording to "hard constraint" in the task prompt's selection criterion.
- Add explicit cluster-shape taxonomy for the subagent to use (strategy-heavy / tactical / human-centered / structural / financial / risk-focused / opportunity-focused — drawn from the dimensions mapping in `phase2D_brainstorming-personas.md` and the topic shapes visible in the four `effort-comparison.md` memos).
- Add a verification step in the deliverable: each (topic, med) pair and (topic, high) pair must explicitly name the two distinct shapes; if shapes can't be diversified for a topic, document the reason and flag for the user to override.

## Baselines (BL1)

### Q4 — Hybrid vs. from-scratch ledger construction (med + high samples)

**Decision:** From scratch only. Build the through-line ledger from `responses/{cluster}/*.md` directly; do not seed from existing `synthesis/attributed/{cluster}.md`.

**Why:** The `attributed/` file was generated by the prompt under test. Using it as a seed risks circular reasoning: BL1's ground truth would inherit any biases the prompt had (dropped through-lines, fabricated attributions, smoothed convergences), and FA1 would then score the prompt against a ledger the prompt itself shaped. From-scratch construction guarantees the ledger is uncontaminated.

**Tradeoff accepted:** ~2× slower per med/high cell — each per-cell subagent reads 4 (med) or 7 (high) full response files and extracts through-lines without a seed. Acceptable because the cleanliness of the ledger is load-bearing for FA1's entire conclusion.

**Action for BL1 task file:**
- Remove the "hybrid seed" step from the per-cell subagent prompt for med + high cells.
- Reframe Step 1 ("Build the through-line inventory") as universal across all efforts: read all persona response files; extract through-lines from raw responses only.
- Keep the existing `synthesis/attributed/{cluster}.md` files as a *post-baseline cross-reference only* — after the ledger is built, the subagent may compare its ledger to `attributed/` and flag discrepancies for FA1 (additional through-lines, missing through-lines, re-attributions). These flags inform FA1 but do not modify the ledger.
- Rename the "Hybrid-Audit Notes" section in the deliverable to "`attributed/` cross-reference notes" with the same content but framed as one-way (ledger → comparison), not seed-with-audit.

### Q5 — FA1 scoring rubric for "dropped persona name"

**Decision:** Strict for med (4 personas, low ambiguity), weighted for high (7 personas, more legitimate aggregation pressure).

**Why:** At 4 personas the synthesis prompt has minimal aggregation pressure — any dropped persona is unambiguously a failure. At 7 personas, some persona-merging is legitimate when convergence is strong, so partial credit (wrong-attribution = 0.5; complete drop = 0; correct = 1) better captures whether the prompt is failing structurally vs. making reasonable aggregation calls.

**Note:** This rubric applies to `attributed/{cluster}.md` only — see Q6 below for the broader reframing of how persona names should be treated in `_synthesis.md` and `_summary.md`.

**Action for FA1 task file:** No change to the rubric itself — already pinned to med-strict / high-weighted in the per-sample subagent prompt's Axis A. But the framing needs to clarify that Axis A scores `attributed/{cluster}.md` *only*. See Q6 action.

### Q6 — FA1 pass threshold + persona-naming policy in non-attributed outputs

**Decision:** **Personas should NOT be named in the prose of `_synthesis.md` or `_summary.md`.** They should appear by name only in `attributed/{cluster}.md` (the transparency document) and in attribution sub-bullets within it. Everywhere else, framing is by stance ("a feasibility-oriented case argues…; a risk-oriented counterpoint flags…"), not by persona name.

**Source instruction quoted by user:** From `idea-symphony/prompts/phase4_summary-only_low-effort.md`: *"Your summary must preserve this tension — the value of `low` effort is specifically in the critical + pragmatic contrast. **Frame that tension substantively in the output** (e.g., 'a feasibility-oriented case argues…; a risk-oriented counterpoint flags…') rather than naming the personas in the prose. The final BRAINSTORM.md should read as a portable analysis that a cold reader — someone unfamiliar with this skill — can follow, not as a transcript of two named characters."*

**Why:** The portable-analysis principle. A cold reader of `BRAINSTORM.md` (or any of the per-cluster prose outputs) should not need to know the Symphony skill exists. Persona names are an implementation detail of the brainstorming engine, not a feature of the output. They belong only in `attributed/` where transparency is the explicit purpose.

**Implications for the investigation (not just the threshold question):**

This reframes the FA1 scoring axes:

- **Axis A1 (attributed doc — persona names REQUIRED):** Same as before. Med-strict / high-weighted scoring of persona-name preservation in `attributed/{cluster}.md`. Pass threshold: 90% (per Q5 + this).
- **Axis A2 (synthesis + summary docs — persona names FORBIDDEN):** *New axis.* Any persona name appearing in the prose of `_synthesis.md` or `_summary.md` counts as drift. Pass threshold: zero persona-name occurrences. Strict on every effort level.
- **Axis A3 (distinctive-contribution survival):** *Reframed.* The current "distinctive-through-line preservation rate" axis is split into (a) survival in `attributed/` (with persona attribution — same scoring as A1) and (b) survival in `_synthesis.md` and `_summary.md` (without persona attribution — substance must survive even though the name doesn't appear). The substance-survival metric is what matters for portable analysis.
- **Axis B (hallucinated quotes):** Unchanged. Strict zero-tolerance.
- **Axis C (traceable convergence counts):** Reframed slightly. Convergence claims like "six of seven personas converged" appear in `_summary.md` and `_synthesis.md`. They name a count, not specific personas — that's allowed. But "The Empath flagged X" is a persona-naming statement and is an Axis A2 failure.

**Pass thresholds (consolidated):**
- Hallucinated quotes: zero (strict, every doc, every effort)
- Persona names in `_synthesis.md` / `_summary.md` prose: zero (strict, every effort)
- Persona-name preservation in `attributed/`: ≥ 90% (med strict / high weighted; per Q5)
- Distinctive-contribution survival in `_synthesis.md` and `_summary.md`: ≥ 90% (substance-survival, not name-survival)
- Traceable convergence counts: 100% (every claim verifiable in BL1 ledger)

**Action for FA1 task file:**
- Restructure the per-sample scoring axes from "A / B / C" to "A1 / A2 / A3 / B / C" per the above.
- Add the new Axis A2 scoring step: scan `_synthesis.md` and `_summary.md` for persona-name occurrences; report count and excerpt each.
- Reframe Axis A3 as substance-survival (substance preserved without name) for the prose docs.
- Update the per-sample finding template to include all five axes.
- Update the cross-sample synthesis to surface Axis A2 failures (persona names leaking into prose) as a likely high-priority RP1 target — this is the kind of drift the portable-analysis principle catches.

**Action for PP1 task file:** Add a contract-dimension row to the analysis: "Persona names in prose" — should be FORBIDDEN in `_synthesis.md` and `_summary.md` across all efforts; ALLOWED in `attributed/{cluster}.md`. Flag any prompt that doesn't make this explicit (the current `phase4_full-synthesis.md` says "remove all persona attribution" for Document 2 but is less explicit for Document 3 / `_summary.md`).

**Action for `phase4_full-synthesis.md` (RP1 target):** Make the "no persona names in prose" rule explicit for the `_summary.md` document. Currently the prompt's Document 3 instructions don't address this directly. Adding `"Like Document 2, do not name personas in the prose. Convergence counts (e.g., 'six of seven personas converged') are allowed; specific persona names are not."` to the Document 3 quality standards.

## LB1 (Loss-Budget)

### Q7 — Through-line counting unit

**Decision:** Topic-level claim. One through-line per discrete idea regardless of how many sentences it spans in a response.

**Why:** Matches the unit the four `effort-comparison.md` memos already use (e.g., "11 through-lines, including 'ICU and immigration-law burnout are structurally similar'"). Consistent unit across memos and BL1 ledgers means cross-investigation comparisons stay coherent. Sentence-level counting would inflate the denominator with redundant rephrasings and make survival rates incomparable across cells with different prose density.

**Action for BL1 / LB1 / FA1 task files:** No change — already pinned in all three. Confirms default.

### Q8 — Survival definition

**Decision:** Verbatim + paraphrased = survival; absorbed = separate category (tracked but not counted as survival).

**Why:** Absorption can hide loss-of-signal — a through-line "subsumed into a more general statement" may have lost the actionable specificity that made it useful. Tracking absorption separately surfaces the prompt's tendency to over-generalize without making it a free pass on through-line preservation. Verbatim-only would be too strict (punishes legitimate paraphrasing); all-three-count would mask over-aggregation.

**Action for BL1 / LB1 / FA1 task files:** No change — already pinned in all three. Confirms default.

## RG1 (Cross-Effort Regression)

### Q10 — Diff granularity

**Decision:** Through-line presence (binary) as the primary metric; full-text similarity (continuous) as a backup interpretive aid.

**Why:** Binary presence converts cleanly into actionable RP1 targets ("TL-7 dropped between med and high in topic X"). Full-text similarity catches stylistic drift the binary metric misses (same content, different prose register across efforts) — useful as a backup signal but harder to convert into a single prompt revision.

**Action for RG1 task file:** No change — already pinned. Confirms default.

### Q11 — Within-effort vs. cross-effort signal weight

**Decision:** Report both equally; RP1 iteration triggers on cross-effort drift first.

**Why:** Cross-effort drift is the higher regression risk because effort-conditional branching is a designed feature — drift across efforts means the branching is breaking the prompt's intended evolution. Within-effort instability (med-A vs. med-B variance not attributable to cluster-shape) is also a real signal but a softer trigger — fix cross-effort drift first, then see whether within-effort instability persists.

**Action for RG1 task file:** No change — already pinned. Confirms default.

### Q13 — Variant strategy per prompt

**Decision:** **2 variants for all three prompts** per iteration (escalated from the recommended single-track for full-synthesis).

**Why (user-driven):** Even the mature `phase4_full-synthesis.md` benefits from exploring the design space when revisions are non-trivial — particularly given Q6's persona-naming reframing requires updates to that prompt's `_summary.md` document spec. Treating full-synthesis as mature-and-incrementally-tweaked risks under-exploring the design space when the change is structural rather than stylistic.

**Tradeoff accepted:** Roughly 1.5–2× the regeneration cost per iteration for the full-synthesis prompt. Over 3 iterations × 40 med+high samples × 2 variants = 240 full-synthesis regenerations (vs. 120 in the single-track plan). Acceptable cost for the broader exploration.

**Action for RP1 task file:**
