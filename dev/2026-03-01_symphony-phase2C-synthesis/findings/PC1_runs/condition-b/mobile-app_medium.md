# Brainstorming Questions: Mobile App Simplification

---

## Topic Cluster 01: Defining Core Value and North Star

1. **What "core value" actually means and how we'd find it without usage data**: Beyond the question of which features are used most, what is the underlying job users hired the app to do, what does the product do that no other fitness app does (regardless of whether current users prioritize it), and how would we identify the true differentiator if usage data were unavailable? Is "core value" about aggregate usage or passionate engagement — and what if those aren't the same thing? [Questioner]
2. **Redefining the North Star metric set**: The current metrics (2% DAU/MAU, 47-second sessions, 8% retention) signal product-market fit failure; what leading indicators should replace them, how do we distinguish "better engagement" from "fewer features masking the same problems," and what would a success metric that actually captures core value delivery look like — given that a simpler app might have shorter sessions because users accomplish what they need faster (a perverse "Success-to-the-Successful" incentive where bloat inflates engagement numbers)? [Analyst, Systems Thinker]
3. **Hidden assets and the one thing users would champion**: Among the 180K downloads and the 2% who show up daily, who are they, what specific use case or demographic found value, and — projecting forward — what would users say about an app they genuinely champion three years from now? If the app became known for doing one thing exceptionally well, what would that "I can't live without this" feeling be, and how would it shape onboarding, daily use, and word-of-mouth? [Appreciative Inquirer]
4. **The gateway-drug vs retention-anchor cohort frame**: What distinct user cohorts exist (social users, solo trackers, content consumers), and within each cohort which features serve as "gateway drugs" (on-ramps for users who eventually churn) versus "retention anchors" — recognizing that usage data from a low-retention product conflates these, so a feature that looks popular may actually be "on-ramp to nowhere" for the 92% who leave within 30 days? [Analyst, Devil's Advocate]

## Topic Cluster 02: Feature Prioritization Frameworks

1. **Feature engagement, dependency, and keystone mapping**: What data points beyond usage counts determine which features drive retention (stickiness, cross-feature dependency patterns, correlation with 30-day retention), and which features act as "keystone features" whose removal would cascade through the ecosystem — especially if core value is actually an unexpected combination of 2-3 features working together that silo-level analytics would miss? [Analyst, Systems Thinker]
2. **Small-but-passionate niche as future foothold vs dead-end**: How do we identify features with low adoption but high retention among their users, and distinguish "early adopters of the future core" from "enthusiastic users of a peripheral feature" — given the feedback delay between a small passionate base and mainstream adoption means today's cut could destroy tomorrow's differentiator? [Systems Thinker, Questioner, Devil's Advocate]
3. **Feature popularity vs feature value under skeptical scrutiny**: The 8% retention rate makes usage data potentially misleading — features used early by churning users can appear "popular" while being on-ramps to nowhere. What decision framework could objectively identify core value without letting ownership bias, team politics, or a single PM's framing drive the outcome (a Shifting-the-Burden risk where "research" substitutes one person's judgment for systematic evidence)? [Devil's Advocate, Systems Thinker]
4. **The "simplify into nothing" and execution-quality alternative hypotheses**: What if the real issue isn't feature count but poor information architecture, onboarding, or execution quality across all features — in which case simplification might leave nothing compelling? How do we validate that simplification (not redesign, not discoverability fixes, not quality investments) will actually improve retention before we irreversibly remove features? [Devil's Advocate, Questioner]

## Topic Cluster 03: Unit Economics and Technical Feasibility

1. **Unit economics of feature simplification and runway**: What does per-feature cost structure look like (engineering maintenance, support burden, server costs, opportunity cost), and with 8 months of funding and a team of 8, what's the break-even of different simplification strategies — at what point does simplification trade long-term viability for short-term survival, and is the 8-month runway a false constraint if hidden dependencies or migrations blow up the timeline? [Analyst, Devil's Advocate]
2. **Technical debt and the Fixes-that-Fail removal trap**: How do we quantify maintenance cost embedded in each feature and distinguish "delete-and-forget" from "excise-carefully" features with deep integration — recognizing the Fixes-that-Fail pattern where we cut features to simplify the product, but shared authentication, data models, notification systems, and ghost code leave the technical complexity in place so we never get the simplicity benefit? Could removal cost consume the entire runway without delivering a working product? [Analyst, Systems Thinker, Devil's Advocate]

## Topic Cluster 04: User Segments, Behavior, and Unarticulated Needs

1. **Gaps between what users say and what they do, and unarticulated needs**: The 47-second sessions and 2% DAU/MAU suggest users aren't engaging as intended — what do actual behavior patterns reveal about genuine versus ignored features, and what frustrations or workarounds have users normalized as "just how apps work" that could illuminate the true core value? [Audience Advocate]
2. **Segment-differentiated experiences of bloat**: A 25-year-old fitness enthusiast and a 55-year-old trying to get healthy have different tolerance for complexity; what might we learn from mapping the emotional journey of distinct user types through the current app, and how might "essential" be redefined from the perspective of a single parent with 5 minutes to spare, or someone managing chronic illness who needs simple tracking without cognitive overload? [Audience Advocate]
3. **Emotional journey from open to close**: What specific emotional states do users experience when opening the app, and what determines whether they stay or leave — where in the flow do they feel confusion, frustration, or relief, and at what precise moment do they decide to disengage? [Audience Advocate]
4. **Learning from the 8% who stayed past 30 days**: What would happen if we interviewed these users and asked specifically what they'd stop using if we removed it — would their answers surprise us, and what would those answers reveal about genuine value versus the survivors of a broken system who are effectively already gone? [Questioner, Systems Thinker]

## Topic Cluster 05: Equity, Access, and Power Dynamics

1. **Accessibility, literacy, and language barriers to 15 features**: An app with 15 features and complex navigation likely presents significant barriers; how would feature prioritization change if we centered users with limited digital literacy, non-English speakers, or users who rely on assistive technologies, and how might the notification and feature overload disproportionately affect certain user groups — potentially driving away users who'd benefit most from simplification? [Audience Advocate]
2. **Power dynamics in "core" versus "nice-to-have" decisions**: Feature prioritization often reflects the loudest voices and most-visible data; whose needs and use cases are systematically overlooked in determining what's "essential," and how might we surface those marginalized stakeholder perspectives before cuts are finalized? [Audience Advocate]
3. **Self-selection bias and the 92% we never hear from**: Users who respond to surveys or interviews are likely the most engaged minority — optimizing for them risks ignoring the 92% who leave within 30 days. What research methods help us understand why the majority abandon the app without alienating the users who still care, and what guardrails prevent a single PM's sample from becoming "research"? [Devil's Advocate, Questioner]

## Topic Cluster 06: Communication, Trust, and User Co-Creation

1. **Communication strategy that doesn't create dependency or destroy trust**: What's the optimal sequence and messaging for announcing feature removal — how do we balance transparency and trust-rebuilding with minimizing churn, avoiding a Shifting-the-Burden dynamic where heavy "we're simplifying for you" framing makes users dependent on us to interpret the change rather than discovering value themselves, and what metrics tell us whether we're getting it right? [Analyst, Systems Thinker, Audience Advocate]
2. **Repairing trust with burned-out users and framing loss as gain**: Users who stuck around despite poor experience may feel betrayed or skeptical when features they relied on disappear; what would it take to demonstrate genuine commitment to their needs rather than business survival, could the simplification be framed as "focusing on what matters" rather than "taking things away," and what would it feel like to be a user who deeply relied on a now-removed feature? [Audience Advocate, Questioner]
3. **Genuine user co-creation in deciding which features survive**: Rather than communicating decisions after the fact, how could the community be brought into the decision-making process — turning the relaunch into a moment to acknowledge past missteps, invite participation, and design *with* the community rather than *for* them, and how do we honor passionate niche-feature users through a graceful transition that turns potential churn into deeper engagement? [Audience Advocate, Appreciative Inquirer]

## Topic Cluster 07: Transition Strategy — Incremental vs Relaunch

1. **Incremental simplification versus clean relaunch risk profiles**: What are the comparative risks of gradual simplification (user confusion, compromise erosion where "just one more feature" is spared round after round so the product never becomes truly focused) versus clean relaunch (alienating 180K users at once, and the assumption they'll give us a second chance in a market littered with failed "2.0" launches) — and how do we model outcome probability for each approach under our constraints? [Analyst, Systems Thinker, Devil's Advocate]
2. **Cascading churn, withdrawal period, and contingency planning**: Each cut may trigger abandonment from its passionate users, and cutting multiple features simultaneously could compound churn beyond current attrition; during the 3-6 month withdrawal period when habits outlive features, what determines whether frustration dominates (accelerating decline) or transitions to relief (renewed engagement), what's the maximum acceptable user loss, and what contingency exists if simplification backfires? [Devil's Advocate, Systems Thinker]
3. **Testing before committing — shipping removal as experiment**: What would happen if we temporarily disabled one feature per month and measured who complains (or doesn't notice) — what experimental design validates that our chosen 3-4 features actually represent the core value proposition, and what statistical significance thresholds should we set before committing irreversibly? [Questioner, Analyst]

## Topic Cluster 08: Team, Morale, and Organizational Leverage

1. **Team at its best and reimagined after simplification**: When has this team of 6 engineers, 1 designer, 1 PM felt most energized, proud, or effective, what conditions made that moment possible, and what would a day-to-day look like when they're no longer burned out from maintaining 15 half-built features — what product culture would they be building and what impact would they feel they were having? [Appreciative Inquirer]
2. **"Killing darlings" as liberation rather than loss**: Engineers who spent months or years building features now being deleted face a reinforcing dynamic — ownership attachment resists cuts, maintains bloat, increases maintenance burden, lowers morale further. What's the smallest intervention that flips this into proactive pruning, what rebuilds psychological investment after cuts, and how do we help engineers and designers feel proud of simplification rather than feeling they "failed"? [Systems Thinker, Devil's Advocate, Questioner]
3. **Team-aligned product vision and capacity after cuts**: Given the team's existing technical capabilities, design sensibilities, and domain expertise, what simplified product lets them do their best work — and when 6 engineers shift from maintaining 15 features to perfecting 3, what structural constraints prevent the slow return to bloat that would squander the new capacity? [Appreciative Inquirer, Systems Thinker]

## Topic Cluster 09: Experiments, Validation, and the Amplify-What-Works Loop

1. **First low-risk experiments to find the real core**: What small, low-risk experiments could the team run this month to test which features truly represent the core value, how would we measure them, and how do we engage users so they feel part of the product's evolution rather than subjects of it? What structures, principles, or practices would reliably amplify the strengths that are already working (e.g., if social connection is the strongest, what would the whole app look like built around that)? [Appreciative Inquirer]
2. **Building from existing assets as evolution, not restart**: What technical infrastructure, user insights, team skills, community relationships, or learnings from the current feature set are already in place and could be leveraged to make the MVP reset feel like evolution rather than restart? [Appreciative Inquirer]

## Topic Cluster 10: Post-Launch, Growth, and Competitive Positioning

1. **Post-launch dashboard and 30/60/90 validation**: Once we relaunch, what early warning signs and success metrics should we monitor in the first 30, 60, and 90 days to distinguish "users mourning removed features" from "genuine product-market fit" versus "solved the wrong problem"? [Analyst]
2. **Attracting new users differently and aligning promise with delivery**: A bloated app attracts users by promising everything, which sets unrealistic expectations; a focused app attracts fewer but better-matched users. If marketing still emphasizes breadth, users feel betrayed when they discover we only do 2-3 things — and we're pivoting to a different market, so why assume existing users are the right audience for the simplified product? What growth strategy accepts the alignment constraint? [Systems Thinker, Questioner]
3. **Competitive position in a feature-accumulating market**: Competitors emphasize "more stuff"; stripping down makes us look feature-poor on comparison charts. Is this a worse-before-better situation where simplicity creates a compounding word-of-mouth/retention advantage, and where are the inflection points in the transition curve we need to survive? [Systems Thinker]

## Appended Questions (Perspective, Provocation, and Distinctive-Register Personas)

### Provocateur (Append)

1. **What if you kept exactly ONE feature and made it absurdly worse?** Imagine you stripped the app down to just workout tracking, but then removed all logging, history, progress visualization, and data—leaving only the immediate act of pressing a button that says "I worked out" before the app closes itself. What would this useless button reveal about what users actually crave from the tracking experience? *The real insight: is the value in the data or in the ritual of acknowledgment?*

2. **What if you launched a "competitor" that was intentionally terrible?** Create a clone app with all 15 features, but each one is broken in a specific, maddening way—workout tracking only logs every third workout, meal planning displays recipes you can't actually cook, social feed shows posts from people who don't exist. Market it aggressively to your existing users. What does watching them struggle with the anti-version reveal about which brokenness they'll tolerate and which sends them away forever? *The real insight: what if you could discover core value by studying which imperfections function as dealbreakers?*

3. **What if your 180K downloads were 180K different people who never opened the app twice?** Imagine the retention disaster is actually a feature—your app is designed for single-use transformation, like a ceremonial rite of passage after which users are "graduated" and should never return. How would you redesign the onboarding experience to complete someone's entire fitness journey in 47 seconds? *The real insight: what if the lifetime value model is wrong for this problem and the real opportunity is in perfect, self-contained moments?*

4. **What if the app did nothing but DELETE features for the next 8 months?** Every week, one feature disappears permanently with no replacement, no explanation, and no user choice—until month 9 when the app becomes entirely blank. What would user behavior and retention patterns in this controlled demolition reveal about which features create genuine dependence versus which create mere noise? *The real insight: what if feature removal itself—rather than the final simplified state—was the product experience that taught you what matters?*

5. **What if you had to explain this app to someone from 1995 who has never seen a mobile phone?** They understand "fitness," "food," "friends," and "shopping" as physical, non-digital experiences. As you describe your app, which features make sense in their world and which become meaningless? What does the alien-ness of "social fitness" or "digital meal planning" reveal about assumptions you've never questioned? *The real insight: which parts of your product exist only because they're possible in software, not because they actually solve human problems?*

### Storyteller (Append)

1. **What would the "first five minutes" experience look like for a returning user who opens the simplified app for the first time, and what emotional state should we be designing toward?** Imagine it's Tuesday morning and Sarah, who previously faced 15 features and 6 navigation tabs, opens the new version. Walk through what she sees, what she feels, and what she can accomplish in those critical first minutes. How do we ensure the transition from confusion to clarity happens within a single session? What does "success" look like in that first interaction—should she feel relief, excitement, curiosity, or something else entirely?

2. **How might the engineering team's daily work life transform when they shift from maintaining 15 half-built features to perfecting 3-4 world-class experiences, and what "micro-moments" of professional satisfaction will replace the current burnout cycle?** Walk us through the standup meeting six months from now. What language are engineers using to describe their work? How do conversations about quality, testing, and user feedback change when they're not spread thin across a feature graveyard? What moments of pride—seeing a user review, watching usage metrics, shipping a polished experience—replace the current reality of constant bug fixes and technical debt management? How does the team's relationship with the codebase itself evolve when they're not afraid to touch it?

3. **How might the press release, app store description, and launch announcement tell a story that frames simplification as innovation rather than retreat, and what metaphors or analogies would help users and investors see this as a bold step forward?** Consider the difference between "we're removing features because we couldn't make them work" versus "we've discovered what users actually need, and we're cutting away everything else." What story positions this as the company's bravest decision rather than its most desperate? How do we communicate to new users that this simplified version isn't a downgrade, but rather the first version of the product that actually works? What cultural references or parallels—from other companies, from product design history, from everyday life—could make this pivot feel obvious and inevitable in retrospect?

4. **How might the "moment of deletion" unfold for different types of users when features they've incorporated into their routines disappear, and what narrative threads could help them feel excited rather than abandoned?** Consider Marcus, who uses the supplement store feature weekly, versus Priya, who relies on the progress journal as her primary touchpoint. When they open the simplified app and discover these features gone, what happens in the seconds before they either delete the app or give the new version a chance? What story could the app tell them in that moment—and through what channels (push notifications, onboarding, email, in-app messaging)—that would transform a sense of loss into curiosity about the newly focused experience?

5. **What does the "funeral" scene look like when the team decides which features to cut, and how can we turn a potentially demoralizing process into a moment of clarity and shared purpose?** Imagine the product owner standing at the whiteboard with 15 feature cards, knowing that 11 of them are about to be "killed." How does that conversation unfold? What frameworks or rituals could transform this from a series of painful decisions into a collective act of strategic vision? How do we ensure that every person in that room—whether they built the meditation guide or the friend finder—leaves feeling energized about the new direction rather than mourning their specific contribution? What narrative about the company's future could make sacrificing the present feel like a victory rather than a loss?

### Visionary (Append)

1. **[What if fitness wasn't something you track, but something that emerges naturally through a fundamentally different relationship with your body?]** Instead of asking which features to keep or cut, what if we completely reimagined the category: What would a fitness product look like if it were designed around joy, emergence, and organic behavior change rather than metrics, tracking, and discipline? What if the core value isn't "helping people work out" but something entirely different that doesn't have a current analog in the fitness app space?

2. **[What if instead of choosing 3-4 core features, we created a product with no features at all — just a single, coherent behavior that users engage in repeatedly?]** Imagine a fitness app with no tracking, no planning, no social features, no content — just one elegant, repeatable action that somehow produces fitness outcomes. What would that one action be? What if the app became a "one-button" product where pressing that button initiates a cascade of value without requiring navigation, configuration, or decisions?

3. **[Imagine if the app could disappear entirely as an interface and instead become a presence that anticipates and supports without requiring active engagement?]** What would it mean to invert the relationship between user and app — where the app exists not as something you open, but as something that works on your behalf in the background, creating interventions at the moment they're needed without requiring you to navigate tabs or manage features? What would a zero-UI fitness product look like?

4. **[What if the core value isn't any single feature, but the emotional state users hope to achieve through using the product — and what if we could reverse-engineer from that destination rather than from existing features?]** Rather than asking "what features do people use most," what if we asked "what emotional transformation do people seek when they download this app" and built backward from there? What if the product that delivers that transformation doesn't look like a fitness app at all, but resembles something from a completely different domain (therapy, coaching, entertainment, community)?

5. **[What if the 47-second average session isn't a problem to be solved, but the actual product — and what if we leaned into that rather than trying to extend engagement?]** What would it mean to embrace the micro-session pattern and design something that delivers maximum value in under a minute? Could this become a fundamentally new product category — the "instant fitness intervention" that exists in the interstitial moments of daily life? What if the app's role isn't to occupy attention but to punctuate it with brief, transformative experiences?

### Connector (Append)

1. **Feature pruning as ecosystem succession** The challenge of cutting features mirrors ecological succession, where crowded ecosystems self-thin to let dominant species thrive. In forest ecology, "self-thinning" creates space for the strongest organisms to flourish. What if we viewed the 15 features as competing species in an ecosystem — how would we identify which features are the "keystone species" whose presence enables the entire ecosystem to function, and which are the invasive species crowding out the core value?

2. **The IKEA effect paradox in user attachment** There's a structural parallel between users attached to niche features and the psychological phenomenon known as the IKEA effect — people overvalue things they've invested effort in building or using. But behavioral economics also shows the "endowment effect" creates irrational attachment to things simply because we own them. How do we distinguish between genuine value-creating features and features users are irrationally attached to due to sunk-cost fallacy — and could we borrow techniques from "loss aversion" research to help users let go without feeling betrayed?

3. **Museum curation as a model for feature preservation** When museums face space constraints, they don't simply throw away lesser works — they rotate collections, loan to other institutions, or create digital archives. The 15 features likely each have some users (even if small). Rather than binary keep/kill decisions, what if we borrowed from museum curation practices: could some features be "rotated out" (temporarily disabled but preserved), "loaned" (spun off as separate apps), or "digitized archived" (export functionality for power users while removing from core experience)?

4. **Surgical triage vs. architectural restoration** There are two different structural parallels for feature removal: surgical triage (emergency room — save what can be saved, let go of what's too far gone) and architectural restoration (preserve historical integrity while modernizing function). Triage is fast but destructive; restoration is slow but honors the original vision. The 8-month runway creates urgency, but the "jack of all trades" problem suggests vision clarity is needed. Which metaphor better serves this situation — and how does that choice change the feature selection criteria?

5. **UI complexity as information entropy** Information theory uses entropy to measure uncertainty and complexity in communication systems. The current app's 6 navigation tabs plus hamburger menu represents high interface entropy — users must process too much information before finding value. Claude Shannon's work showed that reducing noise increases signal transmission. If we treated every UI element as adding "noise" to the user's cognitive load, what entropy-reduction principles from information theory could guide which elements are signal (essential) versus noise (eliminable)?

- Circle distribution: Core 20 slots (Devil's Advocate ×10, Pragmatist ×10); Inner Ring 20 slots (Visionary, First Principles Thinker, Technical Expert ×2, Simplifier, Accountant, Audience Advocate ×3, Empath ×3, Storyteller, Systems Thinker ×2, Constraint Flipper ×2, Momentum Builder ×2, Futurist). Middle/Outer Ring: none (medium effort caps at 4 personas/cluster; outer-ring personas like Accountant and Technical Expert were pulled in as Inner Ring topic-matches where their financial/technical affinity was a strong fit — consistent with the Topic Affinity Matrix).
- Dominant topic drivers: (1) **user-facing / community** clusters (04, 05, 06, 08) pulled Audience Advocate + Empath + Storyteller repeatedly; (2) **technical/product & financial** clusters (02, 03) pulled Technical Expert, Simplifier, and Accountant; (3) **strategic/vision** clusters (01, 07, 10) pulled Visionary, FPT, Futurist, and Systems Thinker; (4) **implementation/ops** clusters (07, 08, 09) pulled Constraint Flipper and Momentum Builder. No cluster triggered Lawyer or Politician (no regulatory or multi-stakeholder governance dimensions strong enough to justify outer ring at medium effort).
