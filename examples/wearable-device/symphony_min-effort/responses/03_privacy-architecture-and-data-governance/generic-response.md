# Brainstorming Responses: Privacy Architecture and Data Governance

---

## Question 9: On-Device Data Pipeline Boundaries

* **Define a formal data classification schema baked into firmware structure.** Partition firmware into three privilege tiers: raw-sensor tier (ADC drivers, signal conditioning), feature-extraction tier (windowed FFT, RR-interval calculation, SpO2 ratio), and alert-dispatch tier (model outputs, thresholds, alert payloads). The BLE transmission module is compiled exclusively against the alert-dispatch API — it has no linker access to the raw or feature structs. This means the compiler itself enforces the boundary; you cannot accidentally serialize a raw PPG buffer because the relevant type is not in scope for the BLE stack's translation units.

* **Identify the minimum sufficient statistic for each clinical signal and hard-code the schema.** For arrhythmia detection, the app needs the alert timestamp, confidence score, arrhythmia class (e.g., AF vs. bradycardia), and a 30-second RR-interval histogram (not waveform) — roughly 40 bytes. For SpO2, a nightly minimum and 5th-percentile value suffice; no per-second readings cross the boundary. Formalizing this minimum-schema in an IDL (e.g., Protocol Buffers) and auto-generating both the firmware serializer and the app deserializer from the same schema eliminates the class of bugs where a developer adds a raw field "just for debugging."

* **Add a build-time static-analysis check that enforces boundary rules.** Write a custom clang-tidy rule (or a simple grep-and-fail script in CI) that rejects any commit where BLE packet-construction functions call into raw-sensor or DSP-intermediate namespaces. Tag those namespaces with a `RAW_DATA` annotation; the linter treats any function touching a `RAW_DATA`-annotated struct as tainted, and flags paths that reach the BLE serializer. This runs in under five seconds on a firmware codebase of this size, and the failure message is specific enough to catch accidental leakage during rapid feature development.

* **Instrument a runtime tripwire for defense-in-depth.** Even with the static check, add a firmware unit test that exercises the BLE serialization path against a synthetic payload, hashes the output, and fails if the hash length exceeds a threshold that would indicate a waveform was embedded. More concretely: set a hard cap of 256 bytes per alert packet; if serialization ever produces more, the firmware panics and logs a tamper event to the secure audit store rather than transmitting. This runtime guard catches edge cases the linter might miss — for example, a third-party library update that adds fields.

## Question 10: HIPAA Compliance Architecture for Clinical Partnerships

* **Layer a consent-management module on top of the existing user account system without touching firmware.** Clinical partnership data access is app-side and server-side work, not a device redesign. Build a consent ledger in the companion app backend that records per-user, per-study consent events (timestamp, study ID, scope of data authorized, withdrawal timestamp if applicable). When a health system queries aggregate data, the API layer joins on this ledger and silently excludes any user who has withdrawn or whose consent window has expired. Because raw data never leaves the device, the server's consent enforcement operates only on the processed summaries already stored — no re-architecting the device pipeline.

* **Apply differential privacy at the aggregate query layer with a calibrated epsilon budget.** For research institution access to population-level statistics (e.g., "what fraction of consented users showed AF events in the past 30 days?"), implement a query interface that adds calibrated Laplace noise before returning counts or means. Set epsilon = 1.0 per query and maintain a per-user epsilon ledger; once a user's cumulative epsilon is exhausted for the study period, their data stops contributing to query answers. This satisfies HIPAA's minimum necessary standard because even the aggregate result cannot be traced back to an individual, and the epsilon budget makes privacy loss mathematically accountable.

* **Deploy a secure enclave for the de-identification pipeline on the server side.** Health system partners should receive data that has been stripped of all HIPAA direct identifiers (name, device serial, precise timestamps at under 15-minute granularity). Run this de-identification transform inside a hardware-attested confidential computing enclave (e.g., AWS Nitro Enclave or Azure Confidential Computing) so the startup's own engineering team cannot exfiltrate identifiable data even during a breach of normal compute infrastructure. The enclave outputs only the anonymized aggregate, and its attestation certificate can be shared with the health system as evidence of the de-identification guarantee.

* **Implement structured audit logging that covers the four HIPAA required audit domains.** HIPAA's Security Rule requires logging of access, modification, and transmission of PHI. Since processed alerts are potentially PHI in a clinical context, instrument the backend to log: (1) which API client accessed which user's data and when, (2) what query parameters and response shape were returned, (3) any export or de-identification event, (4) any consent state change. Store logs in an append-only structure (write-once S3 bucket with object lock, or a WORM-compliant log service) so they survive even a full database breach. This audit trail also satisfies the requirement for breach notification — you can reconstruct exactly whose data was exposed and when.

* **Design a graduated data access model with tiered partnership contracts.** Tier 1 (wellness partner): aggregate, non-identified statistics via API, no PHI, no BAA required. Tier 2 (research partner): de-identified individual records with consent, BAA required, differential privacy applied. Tier 3 (clinical health system): identifiable records for enrolled patients, full BAA, secure enclave pipeline, per-query audit logging. This tiering means most partners never need the clinical architecture, which keeps the compliance overhead proportional to actual risk.

## Question 11: Privacy-Preserving Sync Protocol

* **Define a concrete threat model with four adversary classes and design controls for each.** Adversary 1: passive eavesdropper on BLE — mitigated by BLE 5.x encrypted advertising and LE Secure Connections pairing (ECDH-based, not legacy PIN). Adversary 2: rogue base station (MITM) — mitigated by requiring the companion app to present a certificate pinned to the startup's CA before any data exchange; the firmware refuses to send alert payloads to an app that fails attestation. Adversary 3: compromised companion app (malware on user's phone) — mitigated by signing each alert packet with a device-private key stored in the microcontroller's secure element; the server can verify packet authenticity independently of the app. Adversary 4: physical device theft — mitigated by encrypting the on-device audit store and wiping the encryption key on five consecutive failed unlock attempts.

* **Treat the companion app as an untrusted relay, not a trusted endpoint.** The key architectural insight is that if raw data never leaves the device, then a compromised app can only steal alert payloads — not waveforms. Lean into this by designing the BLE protocol so the device sends signed, encrypted packets that the app forwards opaquely to the backend; the app never has a decryption key. The backend holds the corresponding device public key (provisioned at manufacturing) and decrypts there. A compromised app learns nothing beyond "this device sent a packet at time T"; it cannot read the alert content or replay old packets (include a counter or timestamp in the signed payload to prevent replay).

* **Handle factory reset mid-study with a cryptographic key rotation and revocation protocol.** When a device factory-resets, it generates a new device keypair and broadcasts a new public key to the backend via the pairing flow. The backend marks the old keypair as revoked with a timestamp. If the device was mid-study, the study coordinator receives a notification that continuity is broken for that device ID; the IRB protocol should specify whether prior data remains valid. This approach avoids the failure mode of an orphaned device continuing to submit data under a stale identity, which would corrupt study cohort integrity.

* **Use BLE bonding with rotating identity addresses to resist passive tracking.** Consumer BLE devices that use a fixed MAC address can be tracked across locations by passive scanners — a meaningful privacy risk for health device users. Configure the firmware to use resolvable private addresses (RPAs) that rotate on a randomized schedule (default 15-minute rotation per BT spec). The companion app uses the IRK (identity resolving key) established at bonding to recognize its own device despite address rotation, while third-party scanners see only ephemeral, unlinkable addresses. This is a standard BLE feature but is often left unconfigured by firmware teams focused on connectivity over privacy.

## Question 12: User Transparency and Control

* **Implement an on-device "data receipt" that shows users exactly what was synced after each session.** Rather than a vague privacy policy, display a post-sync summary directly in the companion app: "Synced at 7:14 AM — 3 alerts (1 AF event, 2 low SpO2), 7-night sleep summary, 0 raw sensor samples." Each line item should be tappable to see the specific values transmitted. This requires the BLE protocol to include a transmission manifest alongside the data, which is straightforward to implement at the protocol design stage but very hard to retrofit. The receipt approach creates immediate, concrete user trust without legal boilerplate, and it creates a natural audit trail the user themselves can screenshot.

* **Build a data-retention control panel with per-category deletion.** Users should be able to delete alert history, sleep summaries, and account data independently — not just as one "delete my account" nuclear option. Implement per-category deletion in the backend and ensure the device's on-board audit log (separate from the cloud store) is also cleared on user request. This satisfies GDPR's right to erasure in the event of future EU market entry, and it builds consumer trust with the 40+ demographic who are often more privacy-conscious than younger users. Technically, this means tagging every stored record with a category label at write time so deletion queries can be scoped efficiently.

* **Design the transparency layer for two audiences: current consumer user and future clinical audit.** These have opposite needs: consumer users want a simple, plain-language summary; clinical auditors want a complete, timestamped, tamper-evident log. Serve both by maintaining two parallel record types. The consumer-facing record is generated by summarizing the audit log at display time — same underlying data, different presentation. When the device seeks FDA 510(k) clearance, the clinical audit log is already there; you add a read-only API endpoint for authorized reviewers without changing the data model. Plan the schema now: every alert record should include model version, input feature vector hash, threshold value, and inference timestamp — all fields that FDA expects for software-as-a-medical-device audit trails.

* **Use a preference-by-action design rather than consent forms for the consumer phase.** Long consent modals are ignored; users click through without reading. Instead, surface data decisions at natural moments: first arrhythmia alert triggers a modal asking whether to share an anonymized alert summary with the research program; first sleep report triggers a prompt about sleep-data retention duration (30/90/365 days). Each decision is stored with timestamp and can be revisited in settings. This preserves meaningful consent without front-loading cognitive burden. When the FDA pathway begins, retrofit these preference events into a formal consent record — they are already timestamped and categorized, so the conversion to clinical-grade consent is a presentation change, not a data architecture change.

* **Expose model confidence scores alongside alerts to set appropriate user expectations.** A key transparency failure in health wearables is binary alerts ("you may have had an arrhythmia") without confidence context. Display the model's posterior probability alongside the alert: "Possible irregular heartbeat detected — model confidence 71%. Consult a physician if this recurs." This reduces panic from low-confidence false positives and educates users about the device's limitations — critical for the 40+ demographic who may over-rely on consumer wellness devices for clinical decisions. For FDA clearance, this display design also pre-empts a common 510(k) deficiency: the requirement to communicate device limitations to end users through the labeling.
