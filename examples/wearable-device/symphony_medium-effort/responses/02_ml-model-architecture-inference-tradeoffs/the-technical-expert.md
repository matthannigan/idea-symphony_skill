# ML Model Architecture & Inference Tradeoffs - The Technical Expert

---

## Model Size, Quantization, and the Accuracy-Energy Curve on the NPU

* **Empirical characterization via silicon bring-up.** From a technical perspective, you need actual silicon measurements before finalizing quantization thresholds. Recommend a design-of-experiments approach: sweep model sizes (2M–8M parameters), quantization levels (INT8, INT4, INT2), and inference frequencies across representative PPG/accel windows. Measure latency, energy-per-inference, and F1 on a validation set reflecting real-world arrhythmia prevalence (~2–5%). This 2–3 week bring-up run will reveal the empirical accuracy cliff; most teams find INT8 loses <2% F1, INT4 loses 5–8%. Plot the Pareto frontier (energy vs. F1) to communicate tradeoffs to product and regulatory stakeholders. Timeline: prioritize this before firmware architecture freeze.

* **Integer-quantized backbone with selective full-precision heads.** A viable approach is keeping the feature-extraction backbone (convolutions, dense layers) in INT8 while keeping the final classification head(s) in FP32. This hybrid preserves decision boundary nuance where it matters—clinical sensitivity/specificity thresholds—while saving 60–70% energy in the heavier convolutional layers. The firmware overhead is minimal (one int8-to-float conversion per inference); battery impact is typically 3–5% vs. full INT8. This shifts the design conversation from "how low can we quantize" to "where does quantization precision become clinically critical"—a conversation you'll need with your regulatory and clinical advisors anyway.

* **Power-aware model search with hardware constraints.** The NPU's memory bandwidth and cache architecture impose hard ceilings on model size independent of accuracy. Rather than treating quantization as a one-knob problem, run an automated neural architecture search (NAS) constrained by your target latency (<500ms per inference on a 5-min sliding window) and NPU memory footprint (<4MB if on-device inference runs alongside sensors). This approach discovers lower-parameter models that may exceed INT8 quantized larger models in accuracy. Tools like TensorFlow Lite Micro or ONNX Runtime can automate this; expect 3–4 weeks. Payoff: you sidestep premature commitment to a specific silicon target while building confidence in your accuracy-power tradeoff curve.

* **Regulatory calibration of accuracy thresholds.** Before committing to INT4 or lower, align with your regulatory strategy. Consumer wellness mode can tolerate F1>85% for arrhythmia detection; FDA 510(k) clinical claims demand F1>95% with stratified performance across age/sex/BMI subgroups. If you're targeting clinical later, quantization decisions now will cascade into future model retraining costs. Recommend a "quantization budget" conversation: product defines minimum acceptable F1, clinical/regulatory defines stratified performance floors, and firmware/ML jointly optimize quantization to meet both. This locks down risk before tape-out.

* **Online calibration and periodic retraining strategy.** Rather than shipping a static quantized model, plan for periodic firmware updates (quarterly or semi-annual) with retrained models. This lets you start with INT8 for launch, monitor real-world false-positive and false-negative rates in the field, and shift to INT4 or mixed-precision only if field data supports it. On-device telemetry—alert timestamps, user corrections—provides signal for retraining. This approach distributes risk: launch with confidence (INT8), learn from millions of hours of real-world data, then optimize quantization with hindsight.

## Multi-Task vs. Single-Task Model Design

* **Separate specialized models for independent inference pipelines.** From a technical perspective, the arrhythmia and apnea detection tasks operate on fundamentally different temporal scales and signal modalities. Arrhythmia lives in the PPG domain (heart-rate intervals, QT variability); apnea lives in the accelerometer and microphone (breathing pauses, oxygen desaturation patterns). A single multi-task backbone would require compromise in both feature extraction and temporal receptive fields. The viable approach is two independent models (~3M params each, INT8, <200ms latency each) running in parallel on disjoint firmware threads. Firmware complexity is actually lower: no shared gradient buffers, no inter-task loss weighting, cleaner model versioning. Battery cost: ~8–12% increase vs. multi-task, but you gain modularity. Recommend this path for launch; you can explore multi-task fusion later if power becomes critical.

* **Multi-task backbone with decoupled output heads and independent thresholds.** A middle ground: share a 4M-parameter convolutional backbone that learns generic cardiac/respiratory signal structure (reducing duplicate feature extraction), then branch into task-specific heads (arrhythmia and apnea classifiers). This saves ~20% energy vs. two separate models while preserving task independence. Key technical detail: the two heads have independent confidence thresholds and alert routing—alerts are not correlated. Firmware complexity is moderate: one model load, two inference calls per cycle. The risk is that the shared backbone may overfit to arrhythmia patterns (the more clinical task), degrading apnea detection. Mitigate by weighting the multi-task loss to balance both tasks' F1 scores and validating on apnea-enriched datasets.

* **Single unified model with confidence-weighted multiplexing.** Advanced approach: train a single model that outputs both arrhythmia and apnea confidences from the same forward pass, then route high-confidence detections to their respective alert channels. This is the most power-efficient (single model, single inference, ~25% energy saving) and simplest firmware story—one model endpoint. However, it creates tight coupling: a model update affects both detection pipelines simultaneously, increasing regression risk. Your testing burden doubles because you must validate the new model across both tasks. False-positive correlation also emerges: if the model drifts, both pipelines degrade together. This approach is ideal if power becomes a critical constraint post-launch, but risky at v1.0 when you're still calibrating clinical thresholds.

* **Hybrid architecture with task-conditional inference.** A sophisticated option: condition inference on detected signal quality. If PPG quality is high and accelerometer noise is low, dispatch to the specialized arrhythmia model; if accelerometer signal is clean and breathing cadence is detectable, dispatch to the apnea model. This multiplexing strategy adapts model selection to signal conditions, reducing unnecessary inference. Firmware overhead is minimal (a few signal-quality heuristics). Battery savings are substantial (~15–20%) if signal-quality switching fires regularly. The downside: you're maintaining two separate models, and debugging false negatives becomes harder ("was it the wrong model choice, or the model itself?"). Reserve this for v2 after you've validated both models in the field.

## Sensor Fusion Architecture, Timing, and Confidence Weighting

* **Temporal alignment with late fusion and per-modality confidence.** From a technical perspective, your four sensors operate on misaligned clocks: PPG at 100Hz, accelerometer at 50Hz, temperature at 1Hz, microphone at 16kHz (for breathing). A viable architecture is late fusion: run independent feature extractors for each modality (PPG→heart-rate intervals, accel→motion artifact score, temp→baseline drift, microphone→breathing frequency), compute per-modality anomaly scores (confidence 0–1), then fuse via a learned weighted combination. The fusion layer is a 4-input dense network (~500 parameters, negligible latency). Timing: resample all modalities to a common 10Hz grid, compute rolling features over a 30-sec window (medical-grade anomaly requires temporal context), then invoke fusion. On-device buffering is ~2.4KB for the rolling window. This approach is interpretable (you can inspect which sensors drove each alert) and modular (add/remove sensors with minimal retraining).

* **Attention-based sensor weighting for motion artifact rejection.** A more sophisticated approach: use a transformer-based fusion layer that learns attention weights over the sensor sequence. Each modality produces an embedding (e.g., PPG→32-dim latent), then a multi-head attention block learns which sensors to trust at each timestep. For example, if accelerometer motion is high, the attention mechanism downweights the PPG signal (which is noise-prone during exercise). This learned weighting is more dynamic than fixed confidence scores; it adapts to real-world signal conditions. Latency cost: ~50–100ms additional inference for the attention computation. Power cost: ~15% increase. Payoff: substantially better specificity on false positives from motion artifacts. Recommended for medium/high-effort designs; low-effort can skip this and use simple late fusion.

* **Early fusion with synchronized windowing and recurrent memory.** If you want to preserve fine-grained temporal relationships (e.g., the exact millisecond when PPG spike coincides with breathing pause), early fusion concatenates raw or lightly-processed sensor signals and feeds them to a convolutional or LSTM backbone. This requires careful timestamp synchronization—likely a firmware-level ring buffer that aligns all modalities to a common clock before buffering. Advantage: the model learns complex temporal patterns (e.g., specific PPG-accel correlations that distinguish real arrhythmias from noise). Disadvantage: the model is data-hungry (needs lots of labeled examples) and less interpretable (you can't isolate which sensor drove the alert). Recommend only if you have access to extensive clinical datasets with aligned multi-modal ground truth.

* **Modular fusion with per-sensor anomaly cascade.** A pragmatic approach for MVP launch: each sensor feeds its own anomaly detector (PPG→arrhythmia scorer, accel→motion artifact detector, temp→fever detector, microphone→apnea scorer). A simple rule engine then combines alerts: "trigger clinical alert only if (PPG_arrhythmia_score > 0.8) AND (accel_motion_artifact_score < 0.3)". No learned fusion, no attention, just logical gates. This is maximally interpretable for regulatory review ("we're checking three independent conditions") and requires minimal on-device buffering. The tradeoff: you're not leveraging the rich correlations between sensors, so sensitivity may suffer. But for v1.0, this buys you time to collect field data, refine thresholds, and upgrade to learned fusion in v2.

* **Hierarchical buffer management with adaptive windowing.** On the buffer side, don't pre-allocate a fixed rolling window. Instead, implement adaptive windowing: if anomaly confidence is rising, extend the buffer backward to capture 60 seconds of history; if confidence drops, shrink back to 30 seconds. This saves RAM when the device is in low-risk states (normal sleep, resting heart rate) and provides rich context when anomalies emerge. Buffer size: typically 10–20KB (a few minutes of multi-modal history). Firmware complexity is moderate—you're managing a circular buffer with dynamic resize logic. Payoff: better accuracy on borderline cases (the model sees more context exactly when it matters) and lower average memory footprint during normal operation.
